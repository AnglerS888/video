# adscan —— HLS 贴片广告段检测器

给一条 m3u8 地址，自动定位片中插入的贴片广告（ad break）区间。

**纯标准库实现**，不需要 ffmpeg / numpy，Windows 直接跑。

## 用法

```bash
python adscan.py <m3u8地址>            # 检测
python adscan.py <m3u8地址> --all      # 附带逐切片明细
python adscan.py <m3u8地址> --fast     # 零下载初筛（只读 playlist）
python adscan.py <m3u8地址> --json out.json
python adscan.py <m3u8地址> --workers 24 --probe 262144   # 调并发 / 探测窗口
```

会自动从 master 播放列表下钻到最高分辨率的 media playlist。
`--probe` 是每段的初始探测字节数，工具会**分级放大**（×3 → ×9 → 整段）直到抓全 SPS/PMT。

## 原理

采集站/资源站把广告用**另一条编码流**独立封装后拼进正片。拼接处必然留下
编码层与封装层的系统性差异。本工具在 4 个**互相独立**的维度上找「少数派异常」：

| 层 | 判据 | 依据 |
|---|---|---|
| 切片层 | `EXTINF` 时长偏离全局众数 | 重新切片的痕迹 |
| 码流层 | PTS 绝对值量级跳变 | 广告是独立时间轴 |
| 编码层 | SPS 指纹 / SPS 的 fps / 色度原色 / SEI 编码器版本 | 广告来自另一条转码管线 |
| 封装层 | PMT 段指纹 | 广告常带自己的 registration descriptor / 广告商标识 |

判定策略（避免单条判据的假阳性）：

- **硬判据**（命中任意一条即判为可疑）：SPS 指纹不同、fps 不同、色度原色标记缺失/不同、
  矩阵系数不同、宽度不同、x264 编码器版本不同、PMT 指纹不同
- **软判据**（需 ≥2 条才判为可疑）：PTS 量级跳变点、时长偏离众数

「段内无 SPS」**不作为判据** —— 探测窗口不足也会导致取不到 SPS，会造成假阳性。

## 实测结果

### 源 A：`v15.wsyzym3u8.com`（624~626 段，20.85 min）

```
正片: 1920x1080 / 25fps / bt709 / x264 core 165 / SPS md5 c79120bb...
广告: #154~#161  5:08.00 ~ 5:23.13  (15.13s)
      · SPS 指纹不同        · fps=30.0(正片=25.0)
      · 缺少色度原色标记     · 编码器 = x264 core 164
      · PMT 指纹不同(带 "und" 标识)
```

### 源 B：`vip.ffzy-plays.com`（189 段，12.57 min，变长切片）

```
正片: 1920x1080 / 25fps / bt709 / SPS md5 c79120bb...（与源 A 相同 → 同一母版）
广告: #89~#93  5:56.56 ~ 6:16.19  (19.63s)
      · SPS 指纹不同(1c42ccb9...)  · fps=30.0(正片=25.0)
```

零误报，两条源精确命中。

### 源 C：`v13.wsyzym3u8.com`（1549 段，51.62 min，同站不同剧）

```
正片: 1280 宽 / 25fps / bt709 / SPS md5 4db19a74…（与源 A 不同 → 不同母版）
广告: #385~#390  12:50.00 ~ 13:01.77  (11.77s)
      · SPS 指纹不同        · fps=30.0(正片=25.0)
      · 缺少色度原色标记     · 编码器 = x264 core 164
      · PMT 指纹不同(带 "und")
      · 宽度=1920(正片=1280)  ← 正片是 720p，广告素材却是 1080p
```

零误报。**广告时长 11.77s 与源 A 第一批完全相同**，但广告段的 ts 文件 md5 全部不同。

## 🔑 站点级广告指纹库（可硬编码的那一类常量）

这是与「正片 SPS 指纹」**完全相反**的一类常量，必须分清：

| | 正片 SPS 指纹 | **广告 SPS 指纹** |
|---|---|---|
| 随什么变 | 随母版变（每部剧不同） | **随插入器/广告库变（同一站点固定）** |
| 能否硬编码 | ❌ 不能 | ✅ **能** |

实测证据：源 A（`v15`/`202609/30/D0B1D0qnTG27`）与源 C（`v13`/`202610/25/MEt06UAxyG27`）
是**两部完全不同的剧、正片母版不同**（`c79120bb…` vs `4db19a74…`），但它们的广告段
SPS 指纹**逐字节一致**，连段内位置结构都一一对应（首段 / 中段）：

```
广告首段  b9a628441195b186ed75d36e0a10bfbb
广告中段  ad2be416397d9a26005ca389cfac44b6
```

→ 同一套广告素材 + 同一条编码管线。工具已内置 `KNOWN_AD_SPS` 表，
命中即作为硬判据；检测结果里也会打印本次的广告指纹，发现新的手动加一行即可。

当前库内容：

| 站点 | 已知广告 SPS 指纹 |
|---|---|
| `wsyzym3u8.com` | `b9a62844…`、`ad2be416…` |
| `ffzy-plays.com` | `1c42ccb9…` |

⚠️ 但**广告素材内容本身不共用**（源 A / 源 C 的广告段 ts 文件 md5 全部不同），
且广告总时长虽然都是 11.77s，切片边界也不同 → **别拿广告素材 md5 当指纹**，
指纹要打在 SPS 上。

## ⚠️ 哪些判据能跨源、哪些只能源内用

| 判据 | 能否跨源 | 说明 |
|---|---|---|
| SPS 指纹 | **能**（母版级） | 正片 `c79120bb...` 两条源一致 → 可当"这条片是不是同一批资源"的指纹 |
| **广告 SPS 指纹（站点级）** | **能，且可硬编码** | 同站广告库编码管线固定，见上节 `KNOWN_AD_SPS` |
| fps / 色度原色 / 分辨率 | **能**（当规则用） | 正片 25fps+bt709、广告 30fps 无 bt709 —— 规则通用，具体数值不要硬编码 |
| 编码器版本 | ❌ **只能源内** | 源 A 正片 `core 165`、源 B 正片 `core 164 r3191 4613ac3`。<br>「core 165 是正片」在源 B 就是错的 → 只能**源内少数派投票** |
| PMT 指纹 | ❌ **源内可选** | 源 A/C 广告段 PMT 带 `"und"` 标识；源 B 全片 189 段 PMT 完全一致 → 该判据在源 B 无信号 |
| EXTINF 众数 | ❌ **源内可选** | 变长切片源自动禁用（偏离率 >20%） |
| 宽度 | ❌ **源内可选** | 源 C 靠它加分（正片 1280 / 广告 1920），但源 A 两者都是 1920 → 无信号 |

**核心用法**：不要把任何具体数值（core 号、fps、分辨率、指纹）当常量硬编码。
工具的判据全是「**本片内找少数派**」——正片是什么就以什么为基线，
偏离基线的才是可疑。唯一可跨源复用的是**规则**，不是数值。

## 关键结论（跨源通用）

1. **正片 SPS 原始字节指纹 = `c79120bb0d34d73d1cb82e75fc0b7e5e`**，两条源一致
   → 同一母版 / 同一条转码管线。这是**最强的单一判据**。
2. **广告段 SPS 指纹每条源各不相同**，且都 ≠ 正片指纹。
3. **广告段 fps = 30fps，正片 = 25fps**（两条源均成立）。
4. **正片 SPS 的 VUI 里标了 `bt709`**（色度原色/传输/矩阵），广告段要么没标，
   要么标成别的 —— 比只看宽高分辨率强得多。
5. **广告来自另一条转码管线**：源 A 广告 `x264 core 164`/30fps/无 bt709，
   正片 `core 165`/25fps/带 bt709。
   ⚠️ 注意：这是**源内**的对比，不能拿"core 165"当正片的通用特征。
6. **PMT 里可能带广告商标识**：源 A 的广告段 PMT 尾部多 6 字节，含 ASCII `"und"`。
7. **广告段 PTS 是独立时间轴**：源 A 广告段首 PTS 回退 94831.9s，退出时跳进 588.1s；
   源 B 是 94738.6s / 680.0s。**两条源的首 PTS 回退量级一致（~9.4万秒）**
   → 是插入器统一的 offset，可作该站群的弱指纹。

## ⚠️ 重要注意事项

**段号不能跨批次复用。** 同一部剧的 m3u8 会随签名批次（约 30 分钟）自动重新切片：

| 抓取时刻 | 段数 | 广告段 | 广告时长 |
|---|---|---|---|
| 11:41 | 624 | #154~#159 | 11.77s |
| 11:57 | 626 | #154~#161 | 15.13s |

段文件名全部更换，同一时刻的广告被截断的长度也不同。
**对外只能给「播放时间区间」，不能给段号。**

## 踩坑记录

- **不要依赖 PAT**：实测本例 PAT 里 `program_map_PID` 字段是坏的（指向 256，
  但真正的 PMT 在 4096）。按 PAT 找 PMT 会全盘失败。正确做法是直接扫
  `table_id == 0x02` 找 PMT，并用 PES `stream_id` 识别视频/音频流。
- **视频轨里可能嵌 CEA-608 明文字幕**（如 `"lock=1:0:0 ..."`），会污染整个 ES
  字节流的 start-code 扫描。必须在**每个 PES 单元内**独立切 NAL，
  不能把整段 ES 拼起来再切。
- **adaptation field 的存在条件是 `afc & 2`**，不是 `afc & 1`；写错会让 offset 整体错位。
- **探测窗口不能太小**：广告段 SPS 常落在段首 128KB 之外，取不到会被误判成
  「缺少色度标记」。本工具分级放大窗口（128KB → 384KB → 1.1MB → 整段），
  **放大窗口而不是放宽判据**。
- **音频码率不能单独当判据**：画面静止时码率自然偏低，全片有 20+ 段
  码率异常但都不是广告。只能作佐证。
- **变长切片源上 `EXTINF` 众数判据失效**：源 B 众数 4.000 只占 42/189，
  异常率 78%。工具已做自适应（异常率 >20% 自动禁用该判据）。
- **编码器版本基线必须只取正片段**：若把广告段一起计入众数，众数可能落到广告上
  （源 A 当时正片样本只有 1 段，靠巧合选对）→ 反而把正片全判成广告。
  现在基线同时用「SPS 指纹 == 正片」和「PMT 指纹 == 正片」过滤。
- **SEI 载荷前面有 UUID 尾部 / country_code 等控制字节**，直接 latin1 解码会印出乱码
  （如 `îï`）→ 只保留可打印 ASCII。
- **CLI 文档写了 `--workers`/`--probe` 但主入口没解析**（参数是摆设）→ 已修，
  现在真正传进 `ThreadPoolExecutor` 和 `probe_segment()`。
- **切片 URL 带签名，直接 `urlopen` 会 403**：必须带浏览器 UA（`http_get` 已统一处理）。
  没有 UA 时请求会被拒，报 `HTTP Error 403`。
